## What Task-Spec should borrow

| Pattern | Source signal | Task-Spec application |
|---|---|---|
| One unmistakable promise | uv and Dagger | Lead with bounded authority and independent proof, not format terminology |
| Proof before depth | mise and uv | Provide one isolated lifecycle command with expected output |
| Named benefits | Dagger | Explain scope, proof, authority, portability, and evidence as memorable pillars |
| Transparent installation | Spec Kit and uv | Separate the source door that works now from tag-dependent release doors |
| Examples that show output | uv and mise | Show the terminal verdicts users should expect at each lifecycle gate |
| Reference stays discoverable | all sources | Keep the full CLI, schemas, trust model, and conformance links below adoption content |

## What Task-Spec should avoid

- A reference manual before the first successful experience.
- Badges or claims that hide a distinction between local proof and hosted CI.
- Installation commands that depend on an unpublished tag without saying so.
- Repeating the same feature in prose, a diagram, and several tables without
  giving each representation a distinct teaching job.
